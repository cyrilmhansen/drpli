# E2E-42/P0 — FILE front-end integrity, measured on oracle objects

The task's first line: "ensure FILE front-end integrity: parser, linker, semantic
actions, option/conflict rules, mode conflict detection, error reporting,
duplicate/conflict handling."  E2E-41/P0 read DR's own listings; this milestone reads
**DR's own objects**, which is the stronger authority because an object cannot have a
typo in a length byte.  Everything below was measured on the `.REL` files under
`golden/e42p0/`, `golden/e42p0b/`, `golden/e42p0c/`, generated by
`PLI_SRC=probes python3 oracle/batch.py` over `probes/E46E1-4`, `E46G1-7`, `E46H1-7`
and resolved against `oracle/passes.json` with `oracle/lib.py:pick()`.

Four things were wrong or missing in this compiler, and all four are now fixed.

## 1. A REPEATED OPTION KEYWORD WAS ACCEPTED.  DR REJECTS IT

Before this commit the parser put every option word into the `io_opts` list and
`lower_open` consumed them positionally: `io_nth opts 1` for the mode, `io_nth opts 2`
for the second.  `open file(f) input input` therefore lowered as a plain INPUT open and
the duplicate was **silently collapsed** — exactly the failure mode
`spec/FRONTEND-INVENTORY.md` section 2 names when it records FILE INPUT as
"ACCEPTED, but the acceptance list flags duplicate/conflict handling as unverified."

Seven probes, one per keyword in the lowered subset, all diagnosed by DR:

| probe | source | DR |
|---|---|---|
| `E46E1` | `open file(f) input input` | `CONFLICT` under the statement, `1 ERROR(S) IN PASS 2`, **no `.REL`** |
| `E46E2` | `open file(f) stream stream input` | `CONFLICT`, `1 ERROR(S) IN PASS 2`, no `.REL` |
| `E46G4` | `open file(f) stream input input` | `CONFLICT`, `1 ERROR(S) IN PASS 2`, no `.REL` |
| `E46H2` | `open file(f) file(f) input` | `CONFLICT`, `1 ERROR(S) IN PASS 2`, no `.REL` |
| `E46G2` | `open file(f) input title('A') title('B')` | `CONFLICT`, `1 ERROR(S) IN PASS 2`, no `.REL` |
| `E46G6` | `open file(f) input pagesize(24) pagesize(24)` | `CONFLICT`, `1 ERROR(S) IN PASS 2`, no `.REL` |
| `E46H6` | `open file(f) input linesize(80) linesize(80)` | `CONFLICT`, `1 ERROR(S) IN PASS 2`, no `.REL` |
| `E46G5` | `open file(f) input environment(b(1024)) environment(b(1024))` | `CONFLICT`, `1 ERROR(S) IN PASS 2`, no `.REL` |
| `E46G7` | `open file(f) direct direct input` | `CONFLICT`, `1 ERROR(S) IN PASS 2`, no `.REL` |

DR's `CONFLICT` is printed **indented under the offending statement**, with the
`** PL/I-80 COMPILATION complete` trailer after it, and the pass-2 tally line
`1 ERROR(S) IN PASS 2` before the program's own listing lines
(`spec/lab-evidence/e2e42-p0/DR-VERDICTS.txt` §1 reproduces the diagnosis form).
No `.REL` is produced, so these are front-end rejections exactly like
`spec/notes/e2e41-p0-file-open-reconnaissance.md` §10's duplicate-`ASSIGN` case.

`check_open_options` now runs **first** in `lower_open`, ahead of the operand
extractions, because DR diagnoses the repetition before it resolves any operand: with
two `FILE` operands, the duplicate is the finding, not "needs exactly one
`FILE(name)'".  `E46H2` used to report the latter and now reports
`OPEN repeats option FILE 2 times` [C285].

**The rule is NOT "any two options together."**  `E46H1
open file(f) keyed direct input` measures `w1 = 0x058C` and DR ACCEPTS it;
`E46H3 record input` and `E46H4 sequential input` both measure `0x0590` and DR accepts
both.  So `KEYED` and `DIRECT` coexist and `RECORD`/`SEQUENTIAL` are accepted beside a
mode.  A `CONFLICT` means one keyword written twice, or two members of the mutually
exclusive MODE group — `E46E3 input output`, `E46H5 output input`, `E46H7 input update`
are that second case.  Both arms refuse here with the diagnosis named, and neither is
presented as a DR layout law it is not.

**The duplicate list is exactly the nine keywords DR was probed with** — `FILE`,
`INPUT`, `OUTPUT`, `STREAM`, `TITLE`, `PAGESIZE`, `LINESIZE`, `ENVIRONMENT`, `DIRECT` —
and no further.  A repeated `OUTPUT`, `KEYED`, `RECORD`, `SEQUENTIAL`, `UPDATE`,
`APPEND` or `PRINT` has never been put to DR, so those keys are not dup-checked.  The
effect is nil anyway: every one of them except `OUTPUT` is refused as an unsupported
option before this matters.  Extending the list would have been an inference about seven
unmeasured spellings. [C285]

The panel now pins twelve `dr-refuses` `REJECTS` rows.  Eleven of them carry the blamed
keyword as their marker (`OPEN repeats option INPUT 2 times` and so on), so a future change
that collapses a duplicate again — or blames the wrong one — fails the gate.  The twelfth,
`E46H7 open file(f) input update`, is a DR `CONFLICT` too but is NOT mirrored by the
repetition rule: `UPDATE` is outside `open_subset_keys`, so the unsupported-option guard
fires first and the pinned marker is `OPEN option UPDATE is outside`.  Its `NEG_META` says
so in those words, because the perimeter there is DR's *outcome* (no `.REL`), not a parity of
diagnosis this compiler does not have.  `E46E3`/`E46H5` are the same conflict in **both** source
orders, and `NEG_META["E46H5"]` records that DR does not normalise the order away.

## 2. THE MODE-LESS OPEN WAS A MY-GAP.  IT IS NOW AN EXACT SPECIMEN

`spec/notes/e2e41-p0-file-open-reconnaissance.md` §12 left probe C — *what does DR do
for an `open file(f)' that names no mode at all?* — as the single missing fact under the
input/output guard, and `open_mode_word` refused it as "no DR witness".  §12 also warned
explicitly that a bare `open` must NOT be assumed to mean the same as `input`.

`E46E4` answers it: DR **accepts** `open file(f);` and measures `w1 = 0x0690` —
bit-for-bit the word of the spelled `open file(f) input` at P081Q:3 and P072H:3.
`E46G3` (`open file(f) stream`) is the same `0x0690`, and `E46G1`
(`open file(f) title('A')`, still no mode) is `0x0E90 = 0x0690` with DR's TITLE bit
added [C287].  So the default is INPUT and the title bit composes with the default
exactly as with a spelled mode.  The guard is now written from measurement, and the
withdrawn refusal is gone: `E46E4`, `E46G1`, `E46G3` are BYTE-EXACT whole objects.

The `stream`-only spelling (`E46G3`) is the case E2E-41/P0 §12's probe D left open in a
different sense: bit `0x0010` alone, with neither direction bit, is `0x0690` -- the SAME
word as the mode-less and the input forms.  So bit `0x0010` does not select a direction;
it is the stream flag the census already records, and `stream` with no mode is not a
third mode.  A refusal that treated `stream` as if it implied `output` would have been
wrong, and this measurement is what rules it out.

## 3. THE OPTION CENSUS WAS COUNTED FROM TEXT, AND TEXT LIES ABOUT OPERAND NAMES

`spec/lab-evidence/e2e41-p0/OPEN-MATRIX.tsv` (E2E-41/P0's own table) derived its option
columns by searching each OPEN's **statement text** for each keyword, and `spec/CLAIMS.md`
[C280] plus the prose inside `open_mode_word` quoted those columns as facts.  The substring
`output` also occurs in a **FILE operand's name**: `open file(input) keyed ...` (KEYFILE:16)
scored an INPUT it does not spell, and `open file(output) ... print` (LOAN2:54, LOAN2:56)
scored an OUTPUT they do not spell.

`spec/lab-evidence/e2e42-p0/census.py` recomputes the census from **parsed option keys** —
the `opts=[...]` lists in `AST-OPEN-SITES.txt`, which is this compiler's own parser output
over all 34 measured historical OPENs — and cross-checks it against the masked-text method.
Output: `OPEN-CENSUS.txt`.  The numbers are now

```
sites=34  file=34  stream=21  input=4  output=7  print=9  title=30  environment=11
          keyed=4  pagesize=4  linesize=2  direct=1  update=1
TITLE operands: literal=25  variable=5
mode partition: INPUT=4  OUTPUT=7  both=0  neither=23,   and 4 + 7 - 0 + 23 = 34 = sites
OUTPUT rows that omit STREAM: 2 (P021:4-5, ENTER:37-38), both of them `keyed'
```

so the corrections, restated in `open_mode_word`'s own comment rather than in a note someone
has to go and read, are:

* **7** rows spell `output`, not 9; **5** of them spell it together with `stream` and **2**
  do not, both `keyed` — not four;
* **4** rows spell `input`, not 5;
* **23** rows name neither mode, not one: `print`, `keyed`, `direct`, `update` and the
  `stream`-with-no-direction forms are all in that set, which is exactly why "a missing mode
  means INPUT" could not be read off the corpus and had to be probed ([C286]);
* **no** row carries both direction bits, which is a fact about every row because the mode
  group is exclusive in DR and DR says so with `CONFLICT` — not a sampling accident.

What did **not** change is the object evidence, and saying so matters: `OPEN-MATRIX.tsv`'s
`w1` column is read from the `.REL`, and 17 of the 34 rows carry the input bit `0x0080`, 16
carry the output bit `0x0040`, one carries neither (UPDATE:31's `update direct`, `0x4D2C`)
and none carries both — `17+16+1 = 34`, a complete partition.  So **11 rows spell a mode
keyword while 33 rows carry a mode bit**, and the 22-row difference is precisely what [C286]
measures.  Nothing this compiler emits was ever derived from the wrong counts, because
lowering reads the parsed option list; what was wrong is the prose that quoted the columns,
in [C280] and inside `open_mode_word`.  [C287] corrects [C280] rather than replacing it.

One more number that had never been counted before: **`title=30`, of which 5 take a variable
operand** — `LOAN2:56`, `COPYLPT:38-39`, `COPYLPT:49-50`, `RETRIEVE:31-32`, `CREATE:22-22`.
Earlier prose said "5 sites in P0 section 5" for the variable titles, which is right, and
`E2E-41/P2b` said "12 literal", which is not: over the 34 historical sites there are 25
literal and 5 variable, 30 in all.  P1b's [C288] routes those 5, and this count is what
sizes it.

## 4. AST-VS-SOURCE: THE OPTION ORDER SURVIVES THE PARSER, SO THE LIST CAN BE READ DIRECTLY

A conflict rule that inspects an option list is only sound if the list preserves the
order in which the source spelled the options.  It does, and that is now *measured* and
not assumed: `spec/lab-evidence/e2e42-p0/ast_vs_source.py` compares, for all 34 measured
`OPEN` statements in the corpus, the option-key sequence the parser produces against the
option words in the source text:

```
sites=34  mismatch=0
```

Every keyword the parser recognises is checked, including `ENVIRONMENT` which the
lowerer refuses, and the comparison is order-sensitive (`io_key` uppercased, source word
lowercased).  This is what licenses `check_open_options` to read the list rather than the
token stream: **a duplicate found in `opts` was a duplicate in the source**, and the
keyword the compiler blames is the keyword DR blames.  The `KEY` column in
`OPEN-CENSUS.txt` and `AST-vs-SOURCE.tsv` name the same spellings, so the nine-keyword
list above is the parser's own vocabulary, not a guess at it. [C286]

## 5. WHAT `w2` IS, AND WHY A TITLELESS OPEN BUILDS IT FROM `B`

E2E-41/P0 §2 stated the OPEN block's shape but not what `INX SP` was for, and my own
first reading of the two forms was that a titleless open pushes a *different* number of
bytes.  It does not: both blocks are 21 or 29 bytes depending on the title route, and the
byte counts are in `OPEN-BLOCKS-E46.txt`.  Disassembling DR's own OPEN blocks over its own objects — `spec/lab-evidence/e2e41-p0/openblocks.py`,
whose E46 output is banked verbatim as `spec/lab-evidence/e2e42-p0/OPEN-BLOCKS-E46.txt` and
whose reading is §5 of `DR-VERDICTS.txt`.  The two blocks that decide it:

```
titleless : XRA A ; MOV B,A ; PUSH B ; INX SP ; LXI H,w1 ; PUSH H ;
            (LXI H,0000 ; PUSH H) x5 ; LXI H,<cb> ; CALL ?OIOOP
titled    : ...same..., and the five zero words are MOV H,B / MOV L,B / PUSH H x5
```

The `INX SP` follows `PUSH B` only in the titleless form, and the total block length is
identical either way.  That is the whole explanation of the `w2` asymmetry: **DR pushes
the title length as a byte, then discards it with `INX SP` — but `B` stays live, still
holding the length.**  A titleless open therefore builds `w2 = 0x0000` from `B` (already
zero) with `MOV H,B / MOV L,B`, while a titled open must reset HL with
`LXI H,0000` because `B` is now a non-zero length.  This is why the two forms have
different instruction mixes for the same five zero words, which `lower_open` documents
rather than normalising away [C282].

It also means the `POP` question is settled by the objects and not by the listing: after
`CALL ?OIOOP` there is **no** `POP`/`POP H` in any of the 30 blocks — `?OIOOP`'s callee
cleans the stack, which is the same convention `spec/notes/e2e41-p1-named-stream-open-get-close.md`
deduced from the 6-byte CLOSE block.  No `PUSH`/`POP` count was changed on assumption.

## 6. REJECTED SPELLINGS THAT ARE MY-GAPS, NOT DR REJECTIONS

Three probes DR **accepts** and this compiler still refuses.  They are recorded as
`my-gap` rows so the panel says so, and none of them is described as DR behaviour:

| probe | DR | our refusal | why it is our gap |
|---|---|---|---|
| `E46H1` `open file(f) keyed direct input` | `ACCEPTS`, `w1 = 0x058C` | `OPEN option KEYED is outside the E2E-41/P3 witnessed subset` | `parser.ml` DOES record `KEYED` (it is in the option-word list at `parser.ml:103`, which is [C264]'s fix), and `open_mode_word` already computes bit `0x0004`; what refuses is `open_subset_keys = [FILE; INPUT; STREAM; OUTPUT; TITLE]`, the guarded list that deliberately holds only what has a byte-exact specimen. |
| `E46H3` `open file(f) record input` | `ACCEPTS`, `w1 = 0x0590` | `OPEN option RECORD ...` | record-attribute lowering. |
| `E46H4` `open file(f) sequential input` | `ACCEPTS`, `w1 = 0x0590` | `OPEN option SEQUENTIAL ...` | the same. |

`E46H1` is the most interesting of the four because the value is already **measured**
(`0x058C`) and only the parser plumbing is missing.  Wiring `KEYED` into the option list
without changing any accepted program's output is a one-line parser change, and its
consequence — a `KEYED` open emitting `0x0004` — is one I can already pin byte-exactly,
so this is deliberately left for the next milestone rather than done here without its
own specimen: adding it now would put a lowering for `0x058C` in the same commit as a
rule about `CONFLICT`, and the two need separate witnesses.

`E46F5` is **not** one of these rows.  Its refusal is
`STATIC on CHAR(14) VARYING is unsampled` [C114], which is a pre-existing, already-cited
storage-class gap and has nothing to do with `TITLE`; the variable title inside it is an
EXACT specimen of the P1b variable-title claim, not a gap.  A previous note called `E46F5` a
TITLE-gap row, and that misdescription is withdrawn here.

## 7. HOW THE VERDICTS WERE DETERMINED, AND WHAT THE `.ERR` FILES ARE

`oracle/batch.py` writes a `.ERR` file for every probe, and a `.ERR` is not always a
diagnosis: `oracle/lib.py:run_pli80` captures `stdout+stderr` from the emulator, and for
a probe DR *accepts* the `.ERR` contains the tail of DR's listing and the CP/M console
echo — `E46G1.ERR` is 1443 bytes ending in `1 ERROR(S) IN PASS 1` for a probe that
produces a clean `.REL`.  So "DR rejects this" was established **only** by the
two-condition rule used in `spec/lab-evidence/e2e42-p0/dr_verdicts.py`:

1. no `.REL` was emitted, **and**
2. `CONFLICT` appears within 50 characters of an `ERROR(S)` tally.

`E46E4`, `E46G1`, `E46G3`, `E46H1`, `E46H3`, `E46H4` and `E46F5` fail condition 1 and are
ACCEPTS; the twelve conflict probes satisfy both.  Every `w1` quoted above was read
out of DR's own CODE bytes at the `LXI H,xxxx` that precedes the `PUSH H` before
`CALL ?OIOOP` — never from a listing — so the table in `DR-VERDICTS.txt` §4 is object
evidence, not transcription.

## 10. LINKED IMAGES, AND WHAT THEY ARE AND ARE NOT EVIDENCE FOR

`E46G1` is linked and banked — `golden/e42p1b-link/E46G1.COM`, reproduced by
`python3 oracle/linkrun.py link --tag e42p0b --out e42p1b-link --names E46G1 --reuse`.  It is
there as the **literal-title contrast** for [C288]'s dispatch proof (its link chain carries
`?SLCTS` and no `?SLVTS`), not as a P0 claim, and the gate does not run it.  `E46E4` and
`E46G3` have no `.COM`: what they pin is the option word and the block shape, both of which
live in the `.REL`, and a linked image of a mode-less open would add only "it runs", which is
a `RUNTIME.tsv` question rather than a front-end one.

Two caveats that apply to every image in `golden/e42p1b-link/`, recorded in its own
`README.txt` and repeated here so nobody reads the bytes as more than they are: the load
module name is truncated and `PLILIB` lands at a different base in each link session, so the
**resolved call addresses are not comparable between images** — only the SYMBOL NAMES in the
chain records carry a claim.
