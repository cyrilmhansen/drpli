# mine_code_bytes / dr_code_bytes  8080 CODE SECTION size in bytes, read from the .REL's own
#                       LINK-DEF-CODE-SIZE record.  This IS the number DR prints in its listing
#                       as `CODE SIZE = 05B0': verified on 2583 DR-produced sizes across the
#                       golden corpus with zero disagreements (python3 tools/relstats.py
#                       --selfcheck golden), so the field is measured against an independent
#                       authority rather than against a formula.
# mine_data_bytes / dr_data_bytes  data section size, from LINK-DEF-DATA-SIZE = DR's `DATA AREA'.
# nbytes                differing BYTES between the two .REL FILES at equal offsets -- a
#                       FILE-level diff, NOT a code-size difference.  DR's .REL is a bit stream
#                       (a clear bit introduces one data byte, a RELOC advances the logical
#                       address by two), so one extra emitted instruction re-synchronizes every
#                       later bit and a large nbytes does not mean many defects.
# PROVENANCE OF THE OLD NUMBERS: every row here was recorded before E2E-35/P0 with the code
# columns holding a count of reldump "DATA code" ITEMS, not section bytes.  Item counts are the
# bytes the file spells out, i.e. the section size minus the operand words fixed up by
# RELOC/CHAIN-EXT items -- 58 for E34G1, whose CODE SIZE is 70.  The counts were re-measured as
# sizes in E2E-35/P0; per-row deltas survived for 16 of 17 rows, and nbytes is unchanged for all
# 17.  NETWORK is the exception: +5 items became +7 SECTION BYTES, because DR and mine also
# differ in how many operand words get relocated.  Any earlier note or claim that quoted an
# item count as a code size understated the excess by the fixup difference.
