== 3. WHAT IS ESTABLISHED FROM THE OBSERVATION ==
  * The OPEN statement carries NO ENVIRONMENT clause.  The source above
    has no `environment(...)' and DR's OPEN word is 0x0E50, in which bit
    0x4000 (the ENVIRONMENT bit, OPEN-MATRIX/W1-BITFIT) is CLEAR; the two
    record-size words w3/w4 are pushed as 0000 by the listing block above.
  * The 13 payload bytes are exactly what the two PUT LIST statements
    write: `'HELLO'' -- list-directed output QUOTES a character literal --
    then `42' RIGHT-JUSTIFIED IN 5 columns, which is the `MVI A,05' width
    DR emits before ?QDCOP for a 2-digit decimal literal (width = p+3).
    No CR or LF appears between them or after them.
  * The 0x1A fill BEGINS at offset 13, immediately after the payload; the
    file is 128 bytes, so there are 115 filler bytes.

== 4. WHAT IS NOT ESTABLISHED (hypothesis, not evidence) ==
  WHY the file is 128 bytes rather than 13 is NOT measured by anything in
  this repository.  CP/M FCB record padding is the obvious hypothesis --
  a CP/M sequential file's directory extent counts 128-byte records, and
  128 is exactly one record -- but the harness exports the file with
  `cpmcp -f <fmt> <disk> 0:NAME dst' (oracle/cpmwork.py `export',
  cpmtools), which takes the length from the directory extent, and
  PLILIB may or may not write the filler.  Nothing
  here separates those: no captured FCB dump, no directory record, no
  second output file of a different length.

  WITHDRAWN CLAIMS.  These sentences were written in earlier phases and
  are false as stated:
    P0 section 11: `E17D opens outf ... environment(f(128),b(8000))
                  title('$2.$2')' -- and `One 128-byte record: independent
                  corroboration of section 6's w4 = F(n)'.
       E17D has no ENVIRONMENT clause at all and its title is '$1.$1';
       the two halves of that sentence are OTHER programs' -- the
       `f(128),b(8000)' is artefacts/ENTER.PLI:37 (w1 0x4D54, title
       '$1.EMP') and `title('$2.$2')' is COPY.PLI:13 / REPORT.PLI:29 /
       probes/P021.PLI:4.  The corroboration of w4 = F(n) that P0 thought
       this gave therefore never existed.
    P1 section 4: `the 128-byte OUT.DAT of E17D comes from an open that
                  spells F(128)'.
    codegen.ml (w3/w4 comment): same sentence.
    E41X5's NEG_META note (and the INVENTORY.txt row generated from it):
    `... 128 bytes, from an open that spells F(128)'.
  What the E17D run DOES corroborate is narrower: that a stream OUTPUT
  open whose option words are all zero, followed by two PUT FILE LIST
  statements and a CLOSE, produced a readable file whose payload is the
  two items -- so the pushed words are accepted by DR's runtime and
  CLOSE flushed the buffer.
