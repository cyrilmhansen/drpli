E2E-40/P9 -- THREE-TERM FIXED ADD: WHAT ROUTE DOES DR TAKE AT A COMPOUND LEFT OPERAND?
Written and committed BEFORE DR saw any of E45S1..E45S7. Baseline HEAD 7edd243 (P8c + its item-0 fix).
Nothing below is derived from a DR run; it is derived from (a) the two authentic DR objects E40S2/E40S4,
(b) DR witnesses already in the repo, and (c) this compiler's own output, which is NOT an oracle.

--------------------------------------------------------------------------------
0. THE DEFECT BEING INVESTIGATED (reproduced on the current build, before any change)
--------------------------------------------------------------------------------
E40S2 (`declare 1 g, 2 h, 3 a fixed, 3 c fixed, 2 b fixed; a=7; c=5; b=9; put list(a+b+c)'):
  DR   0027 LHLD a / 002A PUSH H / 002B LHLD b / 002E POP D / 002F DAD D   <- inner (a+b)
       0030 PUSH H / 0031 LHLD c / 0034 POP D / 0035 DAD D                 <- OUTER, 6 bytes
  mine 0027..002F  identical to DR
       0030 XCHG / 0031 LHLD c / 0034 DAD D                               <- 5 bytes
  DR CODE 0x44 (68), mine 0x43 (67); DATA agrees at 6; the ONLY difference in the whole file is that
  one instruction and the 1-byte shift it causes. E40S4 (leaf declared before the subgroup) is the
  same one instruction. Verified this session with tools/dis80.py + tools/reldump.py [C264].

MB36 and D12 are a genuine DR `(compound) + ordinary` = XCHG, so **"the left operand is compound" is
NOT what selects PUSH H/POP D** -- a rule that fired on compound-left would have to explain both away.
Nothing in the corpus has ever shown DR a three-term add whose right operand is a member at the outer
node (E40S2/S4 are the only two 3-term adds in all 2037 .REL files -- scanned this session) and nothing
has ever shown DR a two-term add whose LEFT is an ordinary scalar and whose RIGHT is a member.

--------------------------------------------------------------------------------
2. THE SURVIVING HYPOTHESES
--------------------------------------------------------------------------------
H2  RIGHT-CLASS.  DR parks the left operand on the stack exactly when the operand being LOADED into HL
    next (the right operand) is a structure member, or is itself compound; otherwise XCHG.
    Explains every row above. This compiler already implements a NARROWER version: it pushes when the
    right operand writes DE, or is compound, or when BOTH operands are members [C260]. The two extra
    E40S2 bytes are the case (compound-left, member-right), which `vinfo_both_members` cannot see
    because its left argument is an expression, not an Eident.
H2' CLASS PAIR (member,member) or (compound,member) only.  Differs from H2 exactly at a
    (ordinary-left, member-right) node. E39S3 pins (member,ordinary)=XCHG but the reverse pair has
    NEVER been shown to DR.
H1  COMPOUND-LEFT.  Refuted twice over by MB36/D12 above; retained here only so the probes can
    re-falsify it in a member context, because MB36/D12 come from the E2E-15/E2E-18 pointer-era corpus
    where the left operand was a multiplication/call ladder rather than a member sum.
H3  TOPOLOGY / GROUPING.  DR might key on the parse tree shape rather than on storage class.
H4  PRIOR REGISTER STATE.  The choice depends on what the previous operation left in DE.  Note for the
    arithmetic: after BOTH routes HL = left+right and DE = the left operand's value, so the outward
    state is identical -- H4 has to be about the *history* of HL, not its content.
H5  A SPECIALIZED CONSECUTIVE-MEMBER ROUTE.  DR has a path for "sum of members" that generalizes no
    further.  If true, probes whose terms mix classes should fall back to XCHG everywhere.

The two pairs that do the work:

     class only.  H2/H2' say XCHG then PUSH (DR 1 byte bigger on S7); H1 says PUSH in both (S3 == S7);
     H5 says XCHG in both.  This is the single-dimension test of the right-operand's class.
  S1 vs S4  -- both end in (compound, member); the inner nodes differ ((ordinary,member) vs
     (member,ordinary)).  E39S3 pins (member,ordinary)=XCHG.  If S1's inner is PUSH and S4's inner is

--------------------------------------------------------------------------------
ADDENDUM -- E45S8, written and committed BEFORE DR saw it, AFTER E45S1..S7 had
--------------------------------------------------------------------------------
The six probes above settled the compound-left case, but they left one disjunct of the shipped
rule untested.  My arm pushes when (i) storing/keeping the left operand destroys DE, (ii) the left
operand is syntactically compound, or (iii) the RIGHT operand is an internal member cell.  S1's
inner node `h + a' is covered by (i) -- and only incidentally by (iii), because `h = ...' follows
and my SHLD-style store reuses HL.  So S1 cannot say whether (iii) is sufficient on its own.

E45S8 removes the store:   put list(h + a);   (h ordinary, a a member, nothing assigned)
  * right-operand class alone (rule (iii), H2 in section 2): DR parks --
      LHLD h / PUSH H / LHLD a / POP D / DAD D
  * "HL must survive because it will be reused as an address": DR does NOT park --
      LHLD h / XCHG / LHLD a / DAD D
  These are 8 bytes apart in one instruction, so a single .REL decides it.  Predicted DR CODE 83
  under the first reading and 82 under the second (this compiler predicts 83 and emits the park,
  because its own generic arm is rule (iii)); DATA 000C either way; console 24 = 17 + 7 in both,
  which is the [C254] point again -- the value cannot see the route, which is exactly why this
  probe exists and why the bytes are the instrument.
  If DR parks, [C271]'s rule stands as written and the `writes_de' disjunct is a coincidence of my
  store lowering.  If DR swaps, the rule is about HL reuse, [C271] must be re-stated, and E45S1's
  agreement was produced by a different mechanism than the one I documented.
