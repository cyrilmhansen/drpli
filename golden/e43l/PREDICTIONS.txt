WHAT IS ALREADY ESTABLISHED, and what this batch is meant to bound
------------------------------------------------------------------
[C165]/[E2E-11 step 1a] measured the self-update ladder on ORDINARY variables across
k = -8..+16 (E22A02..E22A16, E22B01..E22B08), with the selection rule
    |k| <= 3   -> INX H / DCX H repeats
    |k| >= 4   -> LXI B,<k or twos-complement> ; DAD B
[C178] measured that an OUT-OF-RANGE constant on a self-update (LP14, `y = y + 65535') makes
DR emit the general parked ADD form instead of a ladder -- but 65535 is outside hl_const's
range, so it says nothing about k = 17 or k = -9, which ARE in range.
[E42P1] measured ONE member self-update, at k = +5: LHLD / LXI B,0005 / DAD B / SHLD, 256/256
byte-identical, console 10.
The compiler currently applies the ORDINARY-variable range -8..16 to members by analogy
(`ladder_bias_fits'), and refuses a member self-update outside it (E42N3 registered at +100).
That analogy has never been bounded.  THIS BATCH BOUNDS IT.

HYPOTHESES
----------
H1  An internal member is just a fixed-DATA-address cell: it inherits the ordinary ladder
    EXACTLY -- same -8..16 boundary, same |k|<=3 repeat-vs-LXI B selection, same SHLD tail.
H2  Members use a narrower or otherwise different ladder selection (e.g. always LXI B/DAD B,
    or a boundary set by 5 rather than 8/16), because the cell is addressed relative to a
    structure rather than standing alone.
H3  Outside the ladder DR takes the general expression route and, per [C266], then PARKS the
    member store: body becomes ~LHLD/PUSH H/LXI H,*S/MVI A,p/CALL/CALL/POP D/DAD D followed by
    PUSH H/LXI H,<cell>/POP D/MOV M,E/INX H/MOV M,D.
H4  Qualification changes the emitted route even though `a' and `g.a' denote one cell
    (the [C253]/[C257] "no trace" result would then be false for this shape).
H5  DR rejects some tested source form outright (no .REL emitted).

Byte accounting used below: the ladder body is 6 + |k| when it uses repeats (LHLD 3, SHLD 3,
plus |k| single-byte INX/DCX) and 10 when it uses LXI B/DAD B.  E43L1's whole-program CODE is
predicted at 0x3A = 58, matching E42P1, because +5 and -8 both land on the LXI B side.

---------------------------------------------------------------------------------------
E43L1  a = a - 8       negative end of the sampled range
---------------------------------------------------------------------------------------
MINE NOW: LHLD *(a) / LXI B FFF8 / DAD B / SHLD *(a)   code = 0x3A (58)
H1 -> exactly that: -8 is inside the measured ordinary range and on the LXI B side.
H2 -> if the member boundary is tighter than -8, expect repeats-vs-LXI-B confusion or the
      general route: code jumps to >= 0x48 (the parked body adds ~16 bytes).
H3 -> general + parked: 26-byte body, CODE ~= 0x4C.
RELOCATION CHECK (all probes): the LHLD and SHLD must both fix up to DATA+0x0.  A SHLD that
fixes up elsewhere, or a body whose second fixup is +0x1, is a destination bug, not a route
choice.
PREDICTION: H1, 58 bytes, console 92.  Confidence: moderate-high (this is the endpoint the
analogy was drawn from).

---------------------------------------------------------------------------------------
E43L2  a = a - 9       ONE step outside
---------------------------------------------------------------------------------------
MINE NOW: REFUSED by member_store_class ("self-update with a bias of -9").
H1 -> if the ordinary boundary is real, DR must switch shape HERE: the parked/general ADD
      form (H3 is then the mechanism).  Expected CODE ~0x4C-0x50, and the store becomes
      PUSH H/LXI H,<cell>/POP D/MOV M,E/INX H/MOV M,D -- the [C266] parked store, which mine
      already emits for other general values.
H2 -> could still be a ladder (LXI B,FFF7) if the -8 boundary was an artifact of the
      ordinary-variable probes rather than a DR rule; then 58 bytes and my refusal is too
      tight.
DECISIVE: this is the ONLY probe that can show whether -8 is a DR boundary at all.  If DR
ladders at -9, the range in `ladder_bias_fits' is unmeasured on BOTH ends and must be
re-derived, not extended by one.
PREDICTION: H3 (general + parked), i.e. DR does NOT ladder here; my refusal is the right
verdict for the wrong reason unless I implement the general route.  Confidence: low.

---------------------------------------------------------------------------------------
E43M1  a = 32768       lower bound of the admitted literal interval (32768..65535)
---------------------------------------------------------------------------------------
MINE NOW: conversion prefix then the PARKED store: LXI H,*(pool) / MVI A,05 / CALL / CALL /
          PUSH H / LXI H,<cell> / POP D / MOV M,E / INX H / MOV M,D   code = 0x43 (67)
Evidence for the interval is NOT uniform: 65535 was measured at a member (E42P2) and 32768 was
measured only at an ARRAY element (LR7), so the lower bound is a composition, not an
observation.  [C178]'s LP15 note says DR sizes a DEC literal pool cell by digit count; 32768
has 5 digits like 65535, so the prefix should be identical and only the pool VALUE differs --
which makes this the cleanest possible test of whether the interval's lower end behaves like
its upper end at a member destination.
H1 -> byte-identical to mine apart from the literal itself: same 67-byte CODE, same parked
      store, and DR prints or aborts depending on its runtime range check.
H2  -> DR writes 32768 in place with MVI M (would mean the MVI-M rule keys on the destination
      alone and E42P2's parking was about something else).
PREDICTION: H1, including the RUNTIME behaviour: DR's own object should abort with
`ERROR (1), Conversion' as E42P2 did, since 32768 is outside a signed BIN(15).  If it does
NOT abort, the abort in E42P2 is a property of 65535 specifically and my "range check lives
in the runtime library" reading needs revising.  Confidence: moderate.

COST OF BEING WRONG
-------------------
Every prediction above is about a shape, and mine currently emits a shape for all eight
non-refused probes.  If DR parks where I ladder, or ladders where I refuse, the bytes differ
and the specimen stays out of the byte-exact panel -- which is why the whole file is
compared (256/256 or 384/384 style, RELOC included [C264]), not just CODE length, and the
verdict is read off the linked .COM with `tools/dis80.py --com' so operands resolve rather
than appearing as relocation placeholders.
